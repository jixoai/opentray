win32 notify delivery moved from legacy NIF_INFO balloons to WinRT toasts under a per-app AUMID (real-machine Windows 11 evidence 2026-09-23, build 26200). Three stacked defects made win32 notifications completely invisible: (1) the staged `packages/windows-x64/bin/opentray.exe` predated the Sep-18 tray-notification bridge entirely, so notify fell through to the extension DLL's typed broker-bridged rejection on every real machine; (2) the bridge's `Shell_NotifyIconW(NIM_MODIFY, NIF_INFO)` projection carried `dwInfoFlags = 0` (`NIIF_NONE`), which current Windows 11 builds silently DROP — the API still returns TRUE, but no banner, no action-center entry, and no settings trace; (3) even with `NIIF_INFO`, the balloon channel proved untrustworthy: after the user opens the tray overflow flyout (the exact interaction required to reach any tray menu), subsequent balloons stop presenting while `Shell_NotifyIconW` keeps returning TRUE — verified by A/B/C and time-delay probes, while the broker-side diagnostics showed a perfectly matching `(HWND, uID)` channel and `Ok(())` invocations throughout. The amended O1=B delivery half: the bridge still resolves the scope's live tray registration first (`notification_tray_absent` and session ownership semantics unchanged), but presentation is now a WinRT `ToastNotification` posted under `HKCU\Software\Classes\AppUserModelId\<appId>` (DisplayName written once per process; failures are logged and non-fatal). WinRT toasts presented correctly in every probed state, including flyout-open and post-flyout, where balloons die. The "no new identity atom" wording of the original ruling is amended to permit exactly this registry attribution record — no new window, no second tray icon channel. Payload law unchanged (64/256/64 UTF-16 bounds re-validated, subtitle join, silent flag → `<audio silent="true"/>`); `notification_failed` details now carry the failing HRESULT. Seam tests reworked to the toast projection (XML escaping, one-line vs two-line templates, AUMID folding). Both runtime and webview artifacts were rebuilt and restaged from current source (the webview staging had also gone stale since July).

Toast threading law (real-machine 0xC0000005 evidence 2026-09-24, symbolized via WER offset into the debug PDB at `windows_core::imp::generic_factory::IGenericFactory::ActivateInstance`): a first iteration posted each toast from a per-notify thread that called `RoInitialize(MTA)` … `RoUninitialize()`. windows-core caches WinRT factory pointers in process-wide statics, so tearing down the apartment that activated them leaves those caches dangling — the next `ActivateInstance` after an idle period dereferences freed memory and kills the broker exactly when the user's first post-idle notification fires. The production shape is now a single long-lived toast worker thread + mpsc queue: the apartment is initialized exactly once and deliberately never uninitialized (broker lifetime), the bridge thread only enqueues and returns immediately (no WinRT call, no join — also eliminating the transport-deadline expiry observed when a joined worker stalled), and a closed worker channel surfaces as the typed failure. Stress-verified on the real machine: auto-round plus rapid and post-idle menu-click notifications all resolve in ~11ms with banners presenting and zero crash events.
