ext-webview win32 titlebar overlay package-graph fallback (skill-creator 联调 real-machine evidence 2026-09-28: Owner's Win11 26200 carries only OS-provisioned CBS runtimes — 1.6 and 2.2 families with `Microsoft.Internal.FrameworkUdk.dll` under `SystemApps`, but CBS distributions never ship `Microsoft.WindowsAppRuntime.Bootstrap.dll`, so `windowControlsOverlay` show failed with os error 126 and consumers had to degrade to a framed window). Root mechanism: `ensure_windows_app_runtime_available` could only reach the AppWindow titlebar overlay through `MddBootstrapInitialize` exported by the bootstrap DLL; a temporary integration probe (since deleted) proved the OS-public Package Dependency APIs are the complete substitute on CBS machines — `TryCreatePackageDependency` + `AddPackageDependency` add the runtime package to the process graph, after which `RoGetActivationFactory("Microsoft.UI.Windowing.AppWindow")` succeeds with no DLL and no system install. Fallback tier (only after every bootstrap candidate fails, so machines with the redist bootstrap keep today's behavior): iterate CBS dirs containing FrameworkUdk, add the family package to the graph with probe-frozen parameters (minVersion 0, arch `None` — `Neutral` fails resolution with 0x80670016, family iteration required because CBS 1.6 fails Add with 0x80070002 while 2.2 resolves), process lifetime, context intentionally retained. Runtime DLL candidates additionally append absolute CBS-dir paths (LOAD_LIBRARY_SEARCH_DLL_LOAD_DIR) as a last resort behind the package-graph bare name, and both tiers failing still returns the existing typed Unsupported — no capability faked. Accepted visually on the Owner machine via `example:webview-control` (overlay enabled, frameless false, no 126).
